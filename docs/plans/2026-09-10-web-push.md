# Browser Web Push Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Notify opted-in Android, desktop, and supported iOS Home Screen clients about automated queue outcomes and call progress without adding a webhook service.

**Architecture:** Generate one VAPID key pair in protected authentication state, store browser subscriptions and a deduplicated outbox in SQLite, and send encrypted payloads through a maintained Web Push library. A Service Worker displays Japanese notifications and routes clicks back to the correct merchant page.

**Tech Stack:** Push API, Notifications API, Service Workers, Web App Manifest, `pywebpush>=2.5,<3`, FastAPI, SQLite, pytest

**Spec:** `docs/designs/2026-09-10-queue-automation-design.md`

## Global Constraints

- Complete the storage/collection, prediction/automation, and Web console plans first.
- Use `uv`; do not use system Python or `pip`.
- Require an explicit user gesture before requesting notification permission.
- Treat Push endpoints, `p256dh`, and `auth` values as sensitive capability data; never print or log them.
- Store the VAPID private key only in permission-protected `state.json`; expose only the public key.
- Keep every notification title, body, action, and enablement message Japanese.
- Use Web Push only on HTTPS, except browser-supported localhost development.
- Prefer Android and desktop enablement; instruct iOS users to install the Home Screen Web App first.
- Notification failure must never change queue or automation task state.
- Mock all outbound Push delivery in automated tests.
